# استراحة الجود | Jood Rest

كتالوج ونظام حجوزات لاستراحة الجود في العزيزية بالخبر، المملكة العربية السعودية.

> **الحالة الحالية:** الموقع يستقبل طلبات الحجز، ولوحة الإدارة تعمل: الطلبات، والتقويم، والمدفوعات، والعقد PDF، وزر واتساب، والإعدادات، والمرافق، والأجزاء، والأسعار. وبوابة الضيف تعمل. لم يُنفَّذ بعد: رفع الصور والفيديو، ثم النشر على Render. راجع [خطة المراحل](#خطة-المراحل).

## التقنيات

| الطبقة | التقنية |
|---|---|
| الواجهة | React 19، TypeScript، Vite، Tailwind CSS 4، React Router 7 (RTL بالكامل) |
| الخادم | Node.js 22، Express 5، TypeScript، Zod، Helmet، express-rate-limit |
| قاعدة البيانات | PostgreSQL 16 عبر Prisma ORM 6 و Prisma migrations |
| الاختبارات | Vitest، Supertest، Testing Library |
| النشر | GitHub ← Render (Web Service + PostgreSQL) |

## بنية المشروع

```
jood/

│   ├── src/components/     # مكونات التصميم والتقويم ومكان الشعار
│   ├── src/pages/          # صفحات الكتالوج العشر
│   └── src/styles/         # الهوية البصرية (ألوان وخطوط)

│   ├── src/config/env.ts   # التحقق من متغيرات البيئة
│   ├── src/auth/           # جلسات الإدارة والصلاحيات وحماية CSRF
│   ├── src/settings/       # تعريف إعدادات الموقع (العامة والخاصة) وقيمها الأولية
│   ├── src/services/       # محرك الأسعار وقواعد التعارض
```

في الإنتاج يعمل تطبيق واحد: خادم Express يقدّم الـ API تحت `/api` ويقدّم ملفات الواجهة المبنية من `client/dist`.

## التشغيل المحلي

### المتطلبات

- Node.js 22 (أو 20.19 فأحدث) و npm
- PostgreSQL 16

### الخطوات

```bash
# 1) تثبيت الحزم
npm ci

# 2) إنشاء قاعدتي بيانات للتطوير والاختبار
sudo -u postgres psql -c "CREATE USER jood WITH PASSWORD 'كلمة_مرور_قوية' CREATEDB;"
sudo -u postgres psql -c "CREATE DATABASE jood_dev OWNER jood;"
sudo -u postgres psql -c "CREATE DATABASE jood_test OWNER jood;"

# 3) متغيرات البيئة
cp .env.example server/.env              # ثم عدّل DATABASE_URL و SESSION_SECRET
cp server/.env.test.example server/.env.test

# 4) تطبيق migrations والبيانات الأولية المعتمدة
npm run db:migrate -w server
npm run db:seed:dev -w server

# 5) إنشاء حساب المالك (تُطلب كلمة المرور دون أن تظهر)
npm run create-owner:dev -w server -- --email you@example.com --name "اسمك"

# 6) التشغيل (الخادم على 4000 والواجهة على 5173)
npm run dev
```

افتح `http://localhost:5173`. فحص الخادم: `http://localhost:4000/api/health`.

### الأوامر

| الأمر | الوظيفة |
|---|---|
| `npm run dev` | تشغيل الخادم والواجهة معًا للتطوير |
| `npm run build` | بناء الخادم والواجهة للإنتاج |
| `npm start` | تشغيل نسخة الإنتاج المبنية |
| `npm run typecheck` | فحص الأنواع |
| `npm test` | تشغيل جميع الاختبارات |
| `npm run db:migrate -w server` | إنشاء migration جديدة وتطبيقها (تطوير) |
| `npm run db:deploy -w server` | تطبيق migrations الموجودة (إنتاج) |
| `npm run db:seed -w server` | إضافة البيانات الأولية الناقصة فقط، دون المساس بتعديلات المالك |
| `npm run create-owner -w server -- --email … --name …` | إنشاء أول حساب مالك (يرفض إن وُجد مالك) |

> **ملاحظة عن npm:** يتعطل `npm install` في npm 10.9 بخلل داخلي (`Cannot read properties of null (reading 'edgesOut')`) عند حل الاعتماديات. استخدم `npm ci` الذي يعمل مع npm 10 لأنه يقرأ ملف القفل. لتحديث الحزم استخدم `npx npm@11 install`.

## سير الحجز

1. يختار الضيف التاريخ والاستراحة كاملة أو الأجزاء المتاحة، فيرى السعر من الخادم مع مبلغ التأمين، ويرسل الطلب برقم واتساب. يحصل على رقم طلب مثل `JD-000001`، وتظهر له بيانات التحويل إن أضافها المالك.
2. يصل للمالك إشعار في لوحة الإدارة (جرس الإشعارات)، وعلى واتساب إذا ضُبط WhatsApp Business API.
3. من صفحة الحجز في اللوحة: زر «تأكيد التفاصيل وإرسال العقد» يفتح واتساب برسالة جاهزة. ثم «عرض العقد وتنزيله PDF»، أو «مشاركة» من الجوال مباشرة إلى واتساب.
4. يسجّل المالك «أُرسل العقد» و«ردّ الضيف بـ موافق»، ثم يحوّل الطلب إلى «بانتظار الدفع». تبدأ مهلة الدفع من هذه اللحظة، والطلبات الجديدة لا تنتهي تلقائيًا قبل أن يتواصل المالك.
5. بعد التأكد من وصول المبلغ يسجّل المالك الدفعة، ثم «تأكيد الحجز». لا يمكن التأكيد قبل تسجيل دفعات متحقق منها تغطي مبلغ الحجز.

6. بعد التأكيد: «إنشاء رابط البوابة» ثم «إرسال الرابط للضيف» عبر واتساب (انظر بوابة الضيف أدناه).

صورة إيصال التحويل يرسلها الضيف للمالك على واتساب، ولا يُرفع إيصال في الموقع.

حجوزات جاذر إن أو الهاتف تُسجّل يدويًا من «حجز يدوي / جاذر إن» بقواعد التعارض نفسها، ودون إضافة أي رسوم.

### بوابة الضيف

- رابط خاص لكل حجز مؤكد، مثل `/g/<43 حرفًا عشوائيًا>`، بلا حساب أو كلمة مرور. لا يمكن تخمينه، ويُخزَّن hash الرابط فقط.
- يُنشأ من صفحة الحجز في اللوحة، ويُرسل بزر واتساب، ويظهر للمالك مرة واحدة فقط.
- ينتهي بعد وقت الخروج بعدد ساعات يحدده المالك (12 افتراضيًا)، ويتوقف فورًا عند إلغائه أو إصدار رابط جديد أو إلغاء الحجز.
- يعرض: الترحيب، ورقم الحجز، والموعد، والمحجوز، والتعليمات، وإرشادات المغادرة، والتواصل.
- رمز الدخول والواي فاي يظهران يوم الدخول فقط، أو فورًا إذا اختار المالك ذلك من الإعدادات ← بوابة الضيف.

### رقم باب الاستراحة (TTLock)

- عند تأكيد الحجز يُنشئ النظام عبر [TTLock Open Platform](https://open.ttlock.com) رقمًا سريًا من 6 أرقام. يُضاف للقفل عن طريق البوابة (Gateway)، ويكون صالحًا من وقت الدخول إلى وقت الخروج فقط.
- يظهر الرقم للضيف في بوابته مكان رمز الدخول الثابت (يوم الدخول حسب الإعدادات)، ويراه المالك في صفحة الحجز، ويُحذف من القفل تلقائيًا عند إلغاء الحجز.
- الرقم مشفّر في قاعدة البيانات (AES-256-GCM)، ولا يظهر في سجل العمليات.
- إذا تعذر الاتصال بـ TTLock يبقى الحجز مؤكدًا، ويصل للمالك إشعار بالسبب، ويستطيع إعادة المحاولة من صفحة الحجز.
- الإعداد:
  1. حساب مطور في open.ttlock.com، ومنه `TTLOCK_CLIENT_ID` و`TTLOCK_CLIENT_SECRET`.
  2. بيانات حساب تطبيق TTLock المسجل عليه القفل (`TTLOCK_USERNAME` و`TTLOCK_PASSWORD`) ورقم القفل `TTLOCK_LOCK_ID`، تُضاف في Render.
  3. لوحة الإدارة ← الإعدادات ← قفل الباب ← «اختبار الاتصال»، ثم تفعيل «إنشاء رقم باب لكل حجز مؤكد».
- **لم يُجرَّب على قفل حقيقي بعد:** بُني من توثيق TTLock المنشور، واختُبر بمحاكاة لواجهة TTLock. التجربة الفعلية تكون بعد النشر.

### العقد

- نص العقد المعتمد في `server/src/settings/contract-template.ts`، ويُعدَّل من الإعدادات ← العقد.
- يُملأ لكل حجز تلقائيًا: البيانات، والأسعار، والتأمين، والحساب البنكي، والتعليمات، وسياسة الإلغاء.
- يُنشأ PDF في المتصفح، فتظهر الحروف العربية متصلة واتجاه النص صحيحًا.

### إشعارات واتساب (اختيارية)

1. حساب [WhatsApp Business Platform](https://developers.facebook.com/docs/whatsapp/cloud-api) لدى Meta برقم مخصص للاستراحة.
2. قالب رسالة معتمد من Meta، بمتغيرات بالترتيب التالي: رقم الحجز، اسم الضيف، جواله، التاريخ، المحجوز.
3. في Render أضف `WHATSAPP_TOKEN` و`WHATSAPP_PHONE_NUMBER_ID` و`WHATSAPP_TEMPLATE_NAME`.
4. في اللوحة: الإعدادات ← الإشعارات، أدخل رقمك وفعّل الإرسال.

لم يُجرَّب الإرسال على حساب حقيقي بعد. إذا فشل الإرسال يبقى الحجز والإشعار داخل اللوحة، ويظهر سبب الفشل في صفحة الإشعارات.

### أتمتة رسائل واتساب للضيوف

صفحة «أتمتة واتساب» في لوحة الإدارة (للمالك فقط). **متوقفة افتراضيًا.** ثلاثة أوضاع:
- **متوقفة:** لا يُرسل شيء.
- **تجربة:** تُجهز الرسائل وتظهر في السجل دون إرسال.
- **تشغيل:** تُرسل للضيوف.

| الرسالة | متى |
|---|---|
| استلام الطلب | فور إرسال الطلب من الموقع |
| قبول الطلب | عند «بانتظار الدفع» — المبالغ والتأمين وبيانات التحويل |
| اعتماد الدفع | عند تأكيد الحجز |
| التذكير | قبل الدخول بـ 24 ساعة (قابل للتعديل)، مع المتبقي إن وجد |
| رمز الدخول | قبل الدخول بساعتين (قابل للتعديل) |
| عدم اكتمال السداد | بدل رمز الدخول إذا لم يكتمل السداد |
| الشكر | بعد الخروج بـ 3 ساعات (قابل للتعديل) |

**شروط رسالة رمز الدخول:**
- يُرسل فقط بعد اكتمال سداد مبلغ الحجز والتأمين واعتمادهما.
- يُستخدم رمز TTLock الذي أُنشئ لهذا الحجز نفسه، ولا يُنشأ رمز جديد.
- يُشترط أن يكون الرمز فعّالًا وصلاحيته مطابقة لفترة الحجز تمامًا. إذا فشل TTLock أو لم تتطابق الصلاحية، تُمنع الرسالة ويُنبَّه المالك.
- الرمز لا يُحفظ في السجل (يظهر •••••• بدلًا منه).
- إذا اكتمل السداد بعد منع الرسالة، تُرسل تلقائيًا بالرمز نفسه.

**منع التكرار والموثوقية:**
- رسالة واحدة لكل حجز ونوع، بقيد فريد في قاعدة البيانات.
- الإرسال يتم بمهمة كل دقيقة تحجز الرسائل بـ `FOR UPDATE SKIP LOCKED`.
- الحالة محفوظة في قاعدة البيانات، فلا تضيع بإعادة التشغيل.
- «إعادة المحاولة» تعيد الرسالة نفسها إلى الطابور، ولا تنشئ رسالة جديدة.
- الإرسال المنقطع بسبب توقف الخادم يُعلَّم «فشلت» ولا يُعاد تلقائيًا.

**ما يلزم للتشغيل الفعلي (خارج الكود):**
1. حساب WhatsApp Business Platform (Cloud API) لرقم الاستراحة.
   - للإبقاء على تطبيق واتساب للأعمال على الجوال مع المنصة: خاصية Coexistence، وتتم غالبًا عبر شريك رسمي لـ Meta.
   - **يجب التحقق من أهلية الرقم وشروطها في توثيق Meta وقت التسجيل.**
2. إضافة `WHATSAPP_TOKEN` و`WHATSAPP_PHONE_NUMBER_ID` في متغيرات Render. لا توضع في الكود.
3. إنشاء قالب لكل رسالة في WhatsApp Manager بالنص الظاهر في «نص القالب لـ Meta»، والانتظار حتى يعتمد.
4. كتابة اسم كل قالب في صفحة «أتمتة واتساب»، ثم إرسال رسالة تجريبية لرقم المالك.
5. التبديل إلى «تجربة» ومراجعة السجل، ثم إلى «تشغيل».

ملاحظة: Meta تحاسب على رسائل القوالب حسب فئتها ودولة المستلم.

## محتوى الموقع

- المحتوى في قاعدة البيانات، ويقرؤه الموقع من `GET /api/public/site` عبر `useSiteContent()`.
- القيم الأولية المعتمدة (المرافق والسعات، الأسعار 950 و1,200، تعليمات الاستراحة، أوقات الدخول والخروج، نص تنبيه جاذر إن) معرّفة في `server/src/settings/registry.ts` و`server/src/scripts/seed-data.ts`.
- البيانات التي لم يزوّدها المالك قيمتها `null`، وتعرض الصفحات مكانها تنبيه «قيد الإعداد». لا تُعرض صور أو روابط أو بيانات تواصل مخترعة.
- الإعدادات الخاصة (الحساب البنكي، رمز الدخول، الواي فاي، إعداد الإشعارات، العقد) لا تُرسل للموقع العام أبدًا، ولا يراها إلا المالك.

## قاعدة البيانات

- المخطط: `server/prisma/schema.prisma`.
- الجداول: المستخدمون والجلسات، المرافق، الأجزاء القابلة للحجز (`booking_resources`) والمرافق التي يشملها كل جزء، التعارضات الصريحة، قواعد الأسعار، الضيوف، الحجوزات وبنودها، أقفال منع التعارض، المدفوعات، روابط الضيوف، الإعدادات، الوسائط، الإشعارات، سجل العمليات.

### قواعد التعارض ومنع الحجز المزدوج

- الحجز يكون على «مورد»: الاستراحة كاملة، أو جزء يحدده المالك ويتكون من مرفق أو أكثر. المرافق التي لا تنفصل تُجمع في جزء واحد.
- يتعارض جزءان إذا اشتركا في مرفق، أو إذا سجّل المالك بينهما تعارضًا صريحًا. والاستراحة كاملة تشمل كل المرافق، فتتعارض مع كل الأجزاء تلقائيًا.
- **المنع في قاعدة البيانات نفسها:** كل حجز نشط يحجز صفًا في `booking_locks` لكل (مرفق × يوم)، والمفتاح الأساسي يرفض أي حجز ثانٍ متعارض حتى مع الطلبات المتزامنة.
- عند الإلغاء أو الرفض أو انتهاء الصلاحية تُحرَّر الأقفال تلقائيًا بواسطة trigger في نفس المعاملة، ولا يمكن إنشاء قفل لحجز غير نشط.

### الأسعار

- قاعدة السعر: حسب أيام الأسبوع، أو موسمية لفترة، أو خاصة بتاريخ. الخاصة تتقدم على الموسمية، والموسمية على الأسبوعية.
- **لا يوجد سعر افتراضي:** إذا لم يحدد المالك سعرًا لجزء في يوم ما، فلا يمكن حجزه فيه.
- كل تعديل على المخطط يكون عبر `prisma migrate dev` ويُرفع مجلد `prisma/migrations` إلى GitHub.
- تعمل الاختبارات على قاعدة `jood_test` منفصلة. وتتوقف الاختبارات إن لم يحتوِ `DATABASE_URL` على كلمة `test`، حتى لا تمس بيانات حقيقية.

## النشر على Render

يتضمن المستودع ملف `render.yaml` (Blueprint) يُنشئ:

1. **Web Service** `jood-rest`
   - Build: `npm ci --include=dev && npm run build`
   - Start: `npm run start:render`، الذي يطبّق `prisma migrate deploy` ثم يضيف البيانات الأولية الناقصة ثم يشغّل الخادم
   - Health check: `/api/health`، ويعيد 200 فقط عندما تكون قاعدة البيانات متصلة
   - نشر تلقائي عند كل commit على الفرع المرتبط
2. **PostgreSQL** `jood-db` (الإصدار 16، منطقة فرانكفورت، الأقرب بين مناطق Render للخليج)

### الخطوات

1. ادمج هذا الفرع في `main`.
2. في Render: **New → Blueprint** ثم اختر مستودع `malbusaad/jood`.
3. عند الطلب، أدخل `PUBLIC_BASE_URL` (مثل `https://jood-rest.onrender.com`، أو نطاقك الخاص).
4. يولّد Render قيمة `SESSION_SECRET` تلقائيًا ويربط `DATABASE_URL` بقاعدة البيانات.
5. بعد أول نشر، افتح **Shell** الخدمة في Render وأنشئ حساب المالك:
   ```bash
   npm run create-owner -w server -- --email you@example.com --name "اسمك"
   ```
   تُكتب كلمة المرور في سطر مخفي. لا يعمل الأمر إن كان هناك مالك مسبقًا.

### تنبيه عن الخطط والتكلفة

- **PostgreSQL المجانية في Render تنتهي بعد 30 يومًا** وتُحذف بياناتها، لذلك يستخدم الملف خطة `basic-256mb` المدفوعة حتى تبقى الحجوزات محفوظة.
- خطة الخادم `starter` مدفوعة. الخطة المجانية تتوقف عند عدم الاستخدام وتتأخر في أول طلب بعدها.
- يمكنك تغيير الخطط من `render.yaml` أو من لوحة Render قبل التأكيد.
- **تخزين الصور والفيديو:** نظام ملفات Render مؤقت، لذلك ستُحفظ الوسائط في خدمة تخزين خارجية تُضبط في مرحلة لاحقة.

## الأمان

- لا تُرفع ملفات `.env` أو أي أسرار. كل الإعدادات الحساسة متغيرات بيئة (`.env.example` يوضحها دون قيم حقيقية).
- يرفض الخادم التشغيل إذا كانت متغيرات البيئة ناقصة أو `SESSION_SECRET` أقصر من 32 حرفًا، ورسالة الخطأ لا تعرض القيم.
- مفعّل حاليًا: Helmet (ومنه CSP و`frame-ancestors 'none'`)، وحد معدل الطلبات على `/api`، وحد لحجم الطلب، ورسائل خطأ لا تكشف التفاصيل الداخلية.
- لا يوجد حساب إداري افتراضي. أول مالك يُنشأ بأمر `create-owner` مرة واحدة، والحسابات الأخرى يضيفها المالك.
- كلمات المرور مخزنة بـ scrypt مع salt عشوائي. جلسات الإدارة رمز عشوائي في cookie من نوع `HttpOnly` و`SameSite=Strict` و`Secure` في الإنتاج، ويُخزَّن hash الرمز فقط.
- حماية CSRF: تعديلات الإدارة تقبل JSON فقط، وترفض أي مصدر غير الموقع.
- حد صارم لمحاولات الدخول الفاشلة (10 كل 15 دقيقة لكل عنوان IP)، ورسالة الخطأ واحدة سواء كان البريد موجودًا أم لا.
- الصلاحيات: **المالك** له كل شيء. **الموظف** لا يرى الحساب البنكي ورموز الدخول، ولا يعدّل الأسعار والأجزاء والحسابات.
- سجل العمليات يحفظ من فعل ماذا ومتى، ويحذف منه تلقائيًا الآيبان وكلمات المرور والرموز.
